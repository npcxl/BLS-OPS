## 真 bug：`cd` 不注入标记 → tracked cwd 永远停在登录目录（"明明有路径为什么不存在"）

用户报：终端在 `/opt`（`cd ..` → `cd ..` → `cd opt`），右侧文件面板却报
`路径不存在或已被删除：/root/opt`。

- **根因**：`planCommandSubmission` 把"不弹结果面板"和"不注入标记"混成了
  同一件事（都挂在 `capture` 上）。`cd` 属于 `LOCAL_BUILTINS` → `capture:false`
  → `markers: []` → 没有 OSC 133 D → `onCommandEnd` **永远不被调用** →
  `noteCd` 记下的"待确认目标"没人确认 → tracked cwd 一直停在登录目录 `/root`。
  于是 `cd opt` 被 `resolveCd("/root", "opt")` 解析成 `/root/opt`。
- 这是我 2026-09-24"文件面板跟随终端解析结果"那次改动**暴露**出来的既有空洞
  （改之前面板用自己的 cwd 拼，通常还能对；改之后完全依赖 tracker，就露馅了）。
- **修法**：新增 `CD_FAMILY = {cd, chdir, pushd, popd}`，在 `blocksCapture`
  **之前**拦下：不生成结果面板，但照旧注入 `MARKER_D_LINE`（只要退出码）。
  顺带抽出 `headExecutable()` 复用给 `blocksCapture`；`LOCAL_BUILTINS` 的注释
  加警告 + 指向 `CD_FAMILY`。
  - 刻意**不给** `fg`/`bg`/`eval`/`source` 注入：`fg` 把命令交给前台作业后，
    注入的文本会变成那个作业的输入。
  - 代价（已知并接受）：每次 `cd` 多一个空提示符行 —— 与所有可捕获命令一致
    （标记行本身是一次命令）。换来的是 cwd 准确。
- 测试：`command-plan.test.ts` 拆成「cd 家族注入 D 标记（且不注入 C）」+「其余
  内建一个标记都不写（含 fg/jobs）」+「闭环：plan → CommandBoundaryParser
  → `output_end{exitCode:0}`」。
- 验证：tsc ✓ / pnpm test **768 全过**（55 文件）✓。

## 续：`cd` 失败时面板还是乱跳（同一 bug 的第二形态）

用户复现：终端在 `~`（`ll` 有数据），敲 `cd opt` → shell 报
`No such file or directory`（`~/opt` 确实不存在），右侧面板却跳去 `/root/opt`
并显示"路径不存在或已被删除"，把本来正常的目录列表顶掉了。

- 这次 tracker **解析是对的**（`/root/opt` 就是 `cd opt` 的含义），错在**跟随
  时机**：提交那一刻就乐观跟随 = 把面板带到打错字 / 不存在的目录上。
- **修法（定稿）**：跟随改到**确认成功之后**。
  - `remote-cwd.ts::onCommandEnd` 返回值由 `void` 改为 `string | null`
    （= 确认成功的 cwd；`exitCode !== 0` / `null` / 非 cd 一律 null）；
    `noteCd` 退回 `void`（只写 `pending`，不再对外给"猜的方向"）。
  - `use-terminal-session.ts` 的 `output_end` 分支：拿到非 null 就
    `host.onCwdConfirmed(path)`。
  - `TerminalView`：删掉提交时的 `setFollow(cdTarget)`，改在 host 里给
    `onCwdConfirmed: (path) => setFollow({nonce+1, path})`。
- 测试：`remote-cwd.test.ts` 那个 describe 重写为 4 条 —— 相对路径/`~`与`-`都
  断言 `stateOf().pending`；**新增关键回归**：`cd opt` 打错字 → `onCommandEnd(1)`
  返回 null 且 cwd 不变（面板不动）。

## 事故修复：精简提示符把 `ll` 烙进了提示符（用户报 "`opt# ll` / `~# ll…lavm-er0ycrgnld:~#` 是啥意思"）

上一轮做"远程提示符精简"时，**注入的那一行漏了回车**：`sshInput(sessionId, COMPACT_PROMPT_COMMAND)`，
而那个常量结尾是一个空格、不是 `\r`。

- 后果链条（用户看到的现象逐字对上）：命令从未提交 → 那行字**赖在用户的输入行里**
  → 他接着敲的第一条命令（`ll`）跟它粘成一条 ` [ -n "$BASH_VERSION" ] && PS1='…'ll`
  → bash 拼接相邻引号串，`ll` **进了 PS1 字符串**：命令没执行成，提示符却永久变成
  `opt# ll`（换台机器同理 `~# ll`）。用户说的"乱七八糟""是啥意思"就是这个。
- 他第二次抱怨里的 `lavm-er0ycrgnld:~#` 是**服务器自己画的第一行提示符** —— PS1 只能
  连上之后才改，顺序上抢不到它前面。
- 修法（`terminal-prompt.ts` + `TerminalView.tsx`）：
  - 拆成 `COMPACT_PROMPT_LINE`（不含回车，用于剔除回显）+ `COMPACT_PROMPT_INPUT = LINE + "\r"`
    （真正发送）—— **这是本次核心**。
  - 注入处 `boundaryParserRef.current?.expect([COMPACT_PROMPT_LINE])`：与受控 pwd 探测同一
    机制，回显（含换行）被 `findEarliest` 吃掉，终端里不留这行。
  - `\W` → `\w`：`\W` 只给末级目录名（`/opt` → `opt`），用户看不出在哪一层，会当乱码。
    现在 `~#` / `/opt#` / `/opt/bls-kox#` —— 只去掉 `user@host`，正是他要的"只保留当前路径"。
  - **顺手擦掉服务器那行默认提示符**：注入行尾追加 `&& printf '\033[2K\r'`。依据一个已确认
    的事实 —— 回显连换行一起被剔除，光标正停在服务器那行提示符末尾，于是"擦整行 + 回行首"
    就够，**不做上下移动**，绝不碰上方欢迎信息。
  - 默认值上一轮已改**默认开**（只有主动关过存 `"0"` 才关）：用户明确说"给开关要我自己去开 = 没解决"。
  - i18n 说明文案（组件 + zh-CN + zh-TW）改为"只保留当前路径、去掉 user@host"。
- 注入行变长 → 同步 `command-boundary.ts` 的 `MAX_PARTIAL`(128) 注释，并加断言
  `COMPACT_PROMPT_LINE.length < 128`（超了"半个注入行"在分块边界留不住，回显会漏到屏幕上）。

## 交互修复：Tab 填入候选后按 Esc 把整行清掉了（用户："非常的不智能"）

用户：输入时有提示 → 按 Tab 应用当前那条 → 弹窗还剩别的候选 → 按 Esc 只想关掉弹窗，
**结果刚填进去的命令也一起被清空**。

- 根因：`terminal-suggest.ts::resolveTerminalCompleteKey` 里 **Esc 是无条件 `clear-line`**
  （注释写着"任何状态都清空整行"），expanded 态也不例外。
- 修法（状态感知，语义更准）：
  - 新增动作 `{ type: "collapse" }`：**只收起面板，行内容一个字都不动**；
  - `expanded` 态：`Esc`（顺带把面板底栏一直承诺、但此前直接穿透给 shell 的 `←`）→ `collapse`；
  - `collapsed`（ghost）态：`Esc` 仍是清空整行 —— 没有面板可关时保留老语义（连按两次
    Esc 依然能清行，用户裁决第七条不丢）。
  - `TerminalView` 的 `collapse` 分支 `setSuggestExpanded(false)` + `setActiveIndex(0)`
    （下次 Tab 接受的与面板将显示的首条一致）+ `refocusTerminal()`。
- 文案：`TerminalSuggest` 底栏 + zh-CN/zh-TW `terminal.ts` 改为 `← or Esc to close`（并注明
  "不动已填入的内容"）—— 之前写着 "← to close" 而 `←` 其实什么都不做，是假承诺。
- 测试：`terminal-suggest.test.ts` 改 1 条拆 2 条（expanded Esc/← collapse、无 notice 面板同样只收起 /
  collapsed 与无候选仍 clear-line）。

## 真 bug：精简提示符真正生效后，文件面板再也不跟随（用户："现在为什么不联动了"）

用户追问"这个联动是否做好相应的机制" —— 查完确认是**我上一轮补回车的直接副作用**，链路本身没坏。

- 根因（时序）：精简提示符的 PS1 里带 OSC 7 → **每个提示符都会上报**。一次 `cd` 的输出顺序是
  **提示符先画（OSC 7 已带新目录）→ 我们注入的 D 标记后跑**（标记永远是独立下一行）。
  而 `setFromOsc7` 写着"OSC 7 是权威结果，任何待定的 cd 都作废"（`pending: null`）→
  轮到 D 标记触发 `onCommandEnd(exitCode)` 时 `pending === null` → 返回 null →
  `onCwdConfirmed` 永不触发 → **面板不跟随**。
  在注入行还没带回车（提示符没真正生效）之前根本没有 OSC 7，所以这个洞一直是隐藏的 ——
  这也解释了为什么"偏偏是现在"。
- 修法（机制定稿）：**"权威 cwd 变化" 成为跟随主依据**。
  - `remote-cwd.ts`：`setFromOsc7` 返回 `string | null`（**变了才给路径**）；`feedOutput` 返回
    `CwdReport { path, changed }`。变了 → 跟随并作废 pending（避免 D 标记重复跟随）；没变 → 只在
    "上报值 == 待定目标"（cd 到同一个目录）时保留 pending，其余作废（典型是 cd 失败：cwd 没变，
    绝不能让退出码把面板带进不存在的目录）；**此前完全不知道 cwd（连接后第一次上报）不算变化**
    （否则与面板挂载时的首次加载撞成两次）。
  - `use-terminal-session.ts`：`report.path` → `setCwd`；`report.changed` → `onCwdConfirmed`（主触发点）；
    D 标记 + 退出码降级为**没有 OSC 7 的 shell 的兜底**（`onCwdConfirmed` 的注释同步改）。
- 白拿的能力：复合命令 `cd /x && ls`、`pushd/popd`、`set -P`（物理路径）现在也能跟随 ——
  它们改变的是"上报值"，旧机制只能靠 `cd` + 退出码。
- 测试：`remote-cwd.test.ts` 新增 5 条（OSC 7 先到即跟随且不重复 / 失败 cd 绝不动面板 / 同目录靠 D 标记同步 /
  复合 cd 可跟随 / 无 OSC 7 回退老链路），并把 "picks cwd up from streamed output" 改为断言 `{path, changed}`。
- 验证：tsc ✓ / pnpm test **764 全过**（原 759）✓ / pnpm build ✓ / cargo build ✓（exe 14:16 晚于 dist 14:15）。
