### 本轮踩到并修掉的 10 个真问题（都值得记）

1. **`pub mod proposal;` 忘了加** → 写完 6000 行才发现在 `deployment/mod.rs` 里没声明，
   于是"cargo check 通过"是**空验证**（未被引用的文件根本不编译）。加完立刻冒出 4 个编译错误。
   教训：**新增模块后先故意引用一次（或跑一次 tests），别信第一次 check 的绿**。
2. **文档级"禁用键"扫描误伤 `NativeProcess.args`**：P5.0 的 `args` 是逐项校验过的合法字段，
   不是自由命令。修法：document 级禁用键里去掉 `args`/`argv`，把"禁 args"留给
   `params_json`（那里由 P5.0 的 `validate_params_json` 负责），并加用例钉住两者的边界。
3. **散文里的反引号把生产方案挡下来了**：知识库来源里写了 `` `name@sha256:…` ``，
   而 `$(`/反引号扫描是全局的 → Shell 违规 → 计划被清空。修法：把字符扫描限制在
   **会进命令的子树**（services / domains / workflow / recommended_topology），
   键名扫描仍然全局；两种行为都加了用例。
4. **知识库"声明了冲突但主题不重叠"被当成真冲突**：`kb-selfhosted-db` 声明与
   `kb-compose-multi` 冲突，但两者 topic 完全不交集 → 报出一个无法裁定、也不该存在的
   假问题，直接把计划挡死。修法：**必须同一 topic 才算冲突**（这正是"不静默"的边界，
   不是无限报错）。
5. **`ArtifactDisposition` 未用 / `RiskLevel` 从 proposal::model 导入**（那个 import 是私有的）
   → E0603；`KnowledgeEntry` 缺 Debug；`ServerResourceFacts` 带 f64 却 derive Eq。
6. **工作流自检失败时不给原因**：原来只写"请报告给开发者"。改成把 `validate_plan_graph`
   的错误文本带进 `wf-invalid` note —— 正是靠它一眼看出是 `params_json` 里的 `args` 违规。
7. **`validate_plan_graph` 需要 plan 归属字段非空**：自检时用占位值（"proposal"），
   真正归属在 confirm 阶段填。
8. **方案状态双写不一致**：`mark_proposal_confirmed` 只改列、不重写 JSON（JSON 是不可变快照），
   读回来的方案还说自己是 `draft` → **同一条方案可以被确认两次**。修法：`proposal_from_row`
   里**以列为准**覆盖 JSON 的 status。db 测试抓到的。
9. **`levels.test.ts` 的"必须有译文"把专有名词判成漏翻**（沿用 P5.1 的坑）：VIOLATION_KIND
   里的 `Path`/`Risk` 漏了 zh 译文 → 新增 5 张标签表时一起补齐。
10. **面板测试断言英文拓扑名**：卡片走 `t()`，zh-CN 下渲染的是译文；断言要用 `i18n.t(...)`。

### 关键设计决定（勿回退）

- **AI 边界**：`trait ProposalAdvisor` 只能加批注（`Recommendation` 等级），
  改不动拓扑/工作流/审批/容量；批注不合格进 `AiReview.rejected`（含原因），
  提供方报错也留痕。**当前 `AI_ADVISOR_ENABLED = false`、`ai_review = null`**，
  界面写"AI 未启用（未配置提供方）" —— 不假装分析过。接入只需换 `Some(&advisor)`。
- **可复现**：节点 id = node_key（不用 uuid）；输入/输出哈希都把 id 与时间戳归零，
  所以 `output_hash` 能从库里存的记录重算对账；`generated_at` 不参与哈希。
- **策略钉硬**：`production_requires_approval` / `forbid_secrets_in_artifact` 不可关，
  `min_headroom_percent ≥ 10`；被改松时恢复并记一条 check（`policy-hardened`）。
- **缺字段就清空工作流**：`ready = false` → `workflow.nodes/edges` 为空数组（单测钉住）。
- **回滚是独立汇点**：只有变更类节点的 `on_failure` 边指向它；主链一路 `on_success`。
- **顺带补了容量问卷的 `response_target_ms`**（用户要求里的"响应目标"）：新列 + 新字段，
  填了就**替代**"平均响应 0.5 秒"这条假设（事实取代推断）。

## 补：把 ArtifactAnalysis 接进方案引擎（同日收尾）

用户重发了 P5.2 需求。核对输入清单后发现只差一项：**P5.1 的识别结果（ArtifactAnalysis）
还没进方案引擎**——之前 `ProposalInputs.facts` 一直传空集，并在文档"已知缺口"里如实记着。
这一轮把它接通：

- `deployment/artifact/model.rs`：新增 `ImportSource::source_ref()`。**同一次导入产出的
  所有制品共用这一个 `source_ref`**，所以它是"制品 ↔ 产生它的识别结果"唯一可靠的连接键；
  `commands/deployment_center.rs` 里原来那份局部实现改为委托它（规则只留一处）。
- 新增 `deployment/proposal/facts.rs` + `derive_service_facts()`：
  `ServiceUnit.artifact_id → ArtifactRecord.source_ref → 来源引用相同的导入任务（多次取最近）
  → 该任务的 inspection → name + source_path 对得上的候选`。
  `source_path` 由 `deploy_path` 去掉环境 `deploy_root` 得到；**名字对不上时只按路径回退匹配**
  （环境内重名去重会改写服务名）；**任何一环对不上就返回空事实**——宁可少给，
  也不猜一个看着合理的端口塞进生产方案。
- `commands/deployment_proposal.rs`：读 `list_import_tasks` + 环境的 `deploy_root`，
  把 `facts` 真正填进 `ProposalInputs`（端口 / 健康检查目标 / 环境变量名 / 制品阻断项）。
- 阻断原因用 `serde_json` 取 `FindingKind` 的 **snake_case 键**（与前端
  `FINDING_KIND_LABELS` 同一套取值），前端不用解析自由文本。
- 文档同步：p5.2 的输入表加 ArtifactAnalysis 行、"已知缺口 #2"改成说明**匹配链**与其边界。
- 验证：`cargo test --lib` **468 过**（proposal 34，+4 条正好覆盖：完整匹配 /
  阻断项映射 / 名字被改写时按路径回退 / 匹配不上宁缺勿猜）✓ `cargo fmt --check` ✓

## P5.3 / P5.4 类型化 Workflow Engine + Docker/Nginx/DNS/SSL 部署（同日）

用户要求：类型化 `DeploymentAction`（≥24 个）、类型化执行、生产硬规则、V1 DNS 只做
人工指引 + 解析验证、三栏部署页面。**旧 `commands_json` 不得成为新工作流**。

### 落地结构

- `deployment/action/`：`model.rs`（29 个动作 + 独立输入类型，全部
  `deny_unknown_fields`）、`spec.rs`（穷尽 match 的执行契约：风险/幂等/超时/重试/
  可取消/补偿/前置条件/必需工具）、`validate.rs`（语义与范围：路径在部署根下、
  泛域名禁 HTTP-01、`internal_only` 禁发布端口、密钥条目禁明文）、`compile.rs`
  （计划图 → 动作序列；入口一是 `PlanActionKind`，二是 `params_json.action`
  显式动作；拓扑序排除回滚链与 manual-only 节点）、`tests.rs`(28)。
- `deployment/exec/`：`mod.rs`（ExecContext / SecretScrubber / KeyringSecrets）、
  `steps.rs`（29 个动作的执行 + 解析助手）、`render.rs`（env/compose/nginx 三个
  只吃结构化输入的渲染器）、`guidance.rs`（`DnsProvider` trait + `certificate_plan`）。
- `deployment/run/`：`mod.rs`（EnvironmentLocks / RunRegistry / RunMeta 存
  snapshot_json / RunExecutor：prepare + execute + rollback + save_release）、
  `preflight.rs`（9 类本地可判定检查）、`tests.rs`(16)。
- `commands/deployment_run.rs`：8 个 IPC（preflight/start/approve_node/resume/
  cancel/rollback/dns_guidance/ssl_plan）；事件按**环境**推送。
- 前端：`run-panel.tsx` 三栏页 + `run-panel.test.tsx`(9) + `labels` 两张新表 +
  `zh-CN|zh-TW/deployExec.ts`；DeployView 新增「部署执行」标签。

### 关键决定（值得跨会话记住）

1. **所有新的远程写操作都加在 `safe::Capability`**（新增 17 个变体：MakeDirs /
   Chmod / Checksum / SymlinkForce / ExtractArchive / DockerBuild / DockerPull /
   ComposeUp / ComposeDown / ResolveHost / HttpProbe / CheckTcpPort / CertbotIssue /
   CertbotRenew / ReadLink / RemoveDirectory）。`RemoveDirectory` 是唯一删东西的
   动作，因此额外要求深度 ≥3 且执行器再限"必须在发布根之下"。
2. **命令构造与动作校验共用一份判定**：把主机名/邮箱/URL/权限位/端口/cert 名
   五个校验器从 capability.rs 收进 `safe::validate` 并公开（两处各写一份迟早漂移）。
3. **数据库迁移不执行脚本**：`DatabaseMigration` → `RequireManualStep`（需审批、
   不跑任何东西）。这是"不允许任意命令进入执行路径"的直接体现。
4. **环境锁以环境为键**（不是计划），暂停中也持锁，终态才释放；先加锁再建运行，
   拿不到锁就不留半启动记录。
5. **失败不自动回滚**：留现场 + 三个显式出口（重试本节点 / 从节点继续 / 回滚），
   重试沿用原运行的版本标签（存在 RunMeta 里）。
6. **v12 迁移**：`run_nodes` 加 `action` / `risk_level` 两列（纯新增，旧库就地升级），
   重启后仍能复核"当时执行的是哪个动作"。
