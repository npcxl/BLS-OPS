# P5.3 / P5.4 —— 类型化 Workflow Engine 与 Docker / Nginx / DNS / SSL 部署

本文说明**做了什么、边界在哪、每条安全承诺落在哪个文件**。

---

## 1. 分层：方案 → 编译 → 执行 → 编排

```text
P5.2 方案      DeploymentProposal（给人看：拓扑、容量、风险、未知）
                 ↓ confirm
P5.0 计划      DeploymentPlan + PlanNode / PlanEdge（粗粒度、有 DAG）
                 ↓ compile
P5.3 动作      DeploymentAction（29 个类型化动作、细粒度、可单独重试）
                 ↓ execute
P5.4 执行      safe::Capability → 远程命令 / SFTP 写文件
                 ↑ 编排
P5.3 运行      preflight → lock → run → DAG → events → promote → release → unlock
```

| 模块 | 文件 |
| --- | --- |
| 类型化动作 | `src-tauri/src/deployment/action/{model,spec,validate,compile,tests}.rs` |
| 执行器 | `src-tauri/src/deployment/exec/{mod,steps,render,guidance}.rs` |
| 编排引擎 | `src-tauri/src/deployment/run/{mod,preflight,tests}.rs` |
| IPC | `src-tauri/src/commands/deployment_run.rs` |
| 页面 | `src/workbench/views/deploy/run-panel.tsx` |

**旧 P3 的 `commands_json` 没有进入这条链路**：编译器只吃 `PlanNode`（其
`params_json` 在保存时已被 `validate_params_json` 拒绝 `command`/`cmd`/`args`/`script`），
而动作输入结构体全部带 `deny_unknown_fields` —— 多写一个键就是错误，不是静默忽略。

## 2. 类型化动作（29 个）

需求的 24 个动作全部实现，另加 5 个必要补充：`CheckDependencies`、`ExtractArchive`、
`ComposeDown`、`RestoreNginxBackup`、`RequireManualStep`。

每个动作都有**独立输入类型**与一张执行契约（`action/spec.rs` 的穷尽 `match`）：

| `CheckDependencies` | Low | Safe | 60s | 3 | 是 | — | 会话 |
| `EnsureDirectory` | Low | Idempotent | 30s | 2 | 是 | — | 会话 |
| `PrepareReleaseDirectory` | Low | Idempotent | 60s | 2 | 是 | — | 会话 |
| `UploadArtifact` | Medium | Idempotent | 1800s | 3 | 是 | — | 会话 |
| `VerifyChecksum` | Low | Safe | 300s | 2 | 是 | — | 已上传 |
| `ExtractArchive` | Medium | Idempotent | 600s | 1 | 否 | — | 已校验 |
| `BuildDockerImage` | Medium | Idempotent | 1800s | 1 | 否 | — | 已上传 |

| `ComposeDown` | Medium | Idempotent | 300s | 2 | 否 | — | 会话 |

| `RequireManualStep` | High | Safe | — | 1 | 是 | — | **人工确认** |

**非幂等动作永不自动重试**（`spec.rs` 单测钉住）。每个动作都带唯一审计事件名
`deployment.action.<kind>`。

### 编译规则（计划字典 → 动作）

* `UploadArtifact` → `EnsureDirectory` + 上传 + `VerifyChecksum`（有哈希时）
* `ApplyNginxSite` → `BackupNginxConfig` + `WriteNginxConfig`（**顺序是硬的**）
* `ComposeUp` → `WriteComposeFile`（我们生成的文件时）+ `ComposeUp`
* `ActivateRelease` → `PromoteRelease`（内含切软链；成功后立刻写 `ReleaseRecord`）
* `RestoreRelease` → `RollbackRelease`
* `RequestCertificate` → `VerifyDnsRecord`（HTTP-01 时）+ `IssueCertificate`
* `DatabaseMigration` → `RequireManualStep`（**引擎不执行任何迁移脚本**）
* `FetchSource` / `BuildArtifact` / `PackageArtifact` / `PushImage` → 明确报错
  （V1 不做源码拉取与镜像推送，请在 CI 完成后作为制品导入）

计划节点还可以用 `params_json.action` 直接声明**任意一个**类型化动作
（参数按独立输入类型反序列化），因此 29 个动作全部可达。

## 3. 执行流程

```text
预检（本地可判定的全部判掉）
  → 锁定环境（拒绝第二个并发部署）
  → 创建 DeploymentRun + 全部 RunNode
  → 按编译出的动作序列逐步执行（每步：审批门 → 重试策略 → 记录节点 → 推事件）
  → 健康检查（动作自带，失败即停）
  → PromoteRelease（成功即写 ReleaseRecord）
  → 解锁
```

事件按**环境**推送：`deployment-run-env-<environment_id>`，载荷是
`DeploymentRunDetail`（运行 + 全部节点），前端整体替换状态；轮询 `deploymentRunGet`
是兜底。

### 失败之后

**不自动回滚**（失败留现场）。三个由人触发的出口：

| 出口 | 命令 | 行为 |
| --- | --- | --- |
| 重试本节点 | `deployment_run_resume(run_id, session_id, from_node_key)` | 从该节点重跑；之前的成功节点按库里的记录跳过 |
| 从节点继续 | 同上（不传 `from_node_key`） | 从第一个未完成的节点继续 |
| 回滚 | `deployment_run_rollback(run_id, session_id)` | 执行计划的回滚链；自身也要过审批门 |

重试/继续/回滚**沿用原运行的版本标签**（存在运行元数据里）—— 换一个标签就等于
部署到另一个目录，回滚会对不上。

## 4. 生产环境的六条硬规则（落地位置）

| 规则 | 落地位置 |
| --- | --- |
| 高风险节点单独确认 | `spec::approval_required`（生产 + High/Critical + 有副作用 ⇒ 必须确认）；引擎遇到未批准的步骤**暂停**并写 `RunNodeStatus::Blocked` |
| 禁止两个部署同时改同一环境 | `run::EnvironmentLocks`（键＝环境 id），运行中**含暂停中**持锁，终态才释放 |
| Nginx 写入前备份 | 编译层顺序（备份 → 写）+ `exec::steps::write_nginx` 复核备份文件存在，否则拒绝覆盖 |
| `nginx -t` 通过才 reload | `spec` 的前置条件 + `exec::steps::reload_nginx` **再测一次** |
| DNS 未生效不发 HTTP-01 | `action::validate`（泛域名禁止 HTTP-01）+ `exec::steps::issue_certificate` 现场解析验证 |
| 泛域名只走 DNS-01 | 同上；DNS-01 在 V1 只产出**人工指引**并把人留住（`needs_acknowledgement`） |
| Secret 不进日志与快照 | `exec::SecretScrubber`（值出现即打码）+ 运行快照只存"批准了哪些节点/锁的键/版本标签" |
| Compose 只暴露必要端口 | `action::validate::validate_compose_service`（`internal_only` 的服务**不许**有 `publish_ports`）+ 编译器按角色决定是否发布 |
| 数据库迁移独立审批 | `DatabaseMigration` → `RequireManualStep`（`requires_approval`，且不执行任何脚本） |

## 5. DNS 与证书：V1 的边界

* **只做**：人工配置指引（`deployment_dns_guidance`）+ 自动解析验证
  （`VerifyDnsRecord`，`getent ahosts`）+ HTTP-01 的 certbot 签发（域名已解析且
  certbot 存在时）。
* **不做**：调用任何 DNS 服务商 API。`exec::guidance::registered_providers()` 在 V1
  只有 `manual`，且 `supports_automation() == false`；动作校验层也只接受
  `dns_provider = manual`，所以**不存在**自动写入的路径。
* **预留**：`DnsProvider` trait + `certificate_plan()`（挑战方式、前置条件、为什么
  现在不能签）。接服务商 = 实现 trait + 注册，不需要改动作模型。

## 6. Secret 的处理

1. 模型层：`RuntimeConfigEntry.secret = true` 时**禁止**带明文值，必须有 `secret_ref_id`
   （`action::validate`）。
2. 执行层：值从操作系统钥匙串读（`exec::KeyringSecrets` → `crate::keyring::read_secret`），
   读完立刻登记到 `SecretScrubber`。
3. 日志：所有出站文本都过 `scrubber.scrub()`。
4. 快照：`deployment_runs.snapshot_json` 只存 `RunMeta`（`deny_unknown_fields`，
   不接受任何额外字段）。
5. 分发：密钥值只在写 env 文件时落到服务器，文件模式固定 `600`。

## 11. 已知边界（V1 之外）

1. **不创建 systemd 单元**：`ProvisionService` 遇到 `NativeProcess` 会明确报错，
   要求先把运行方式改成 systemd 或容器形态（写单元文件需要提权与模板治理，
   不在本阶段）。
2. **不拉源码、不推镜像**：`FetchSource` / `BuildArtifact` / `PackageArtifact` /
   `PushImage` 报错并指向 CI。
3. **DNS-01 不自动**：见第 5 节。
4. **回滚不还原数据**：`RollbackRelease` 只切服务版本；`data_note` 会如实写进日志。
5. **TCP 健康检查只支持本机**：`ss` 只能看本机监听表（能力层限制写在校验层，
   不让用户以为是网络问题）。
6. **AI 诊断入口是占位**：`AI_ADVISOR_ENABLED = false` 时按钮禁用并说明原因，
   与 P5.2 一致（不用模板假装分析）。
