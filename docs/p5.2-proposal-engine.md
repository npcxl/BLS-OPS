# P5.2 部署方案生成：规则引擎、知识库与 AI 边界

配套设计文档：`docs/P5_DEPLOYMENT_CENTER_DESIGN.md`（安全模型与分层）。

## 1. 一句话

把"用户想要什么（问卷）+ 服务器是什么（能力事实）+ 制品里有什么（识别结果）
+ 我们知道什么（知识库）+ 我们被允许做什么（安全策略）"变成一份
**可审计、可复现的 `DeploymentProposal`**。

```text
安全策略钉硬 → 知识库检索/冲突裁定 → 容量评估 → 规则引擎（拓扑/服务/工作流/风险/审批/回滚）
  → 组装 →（可选）AI 批注 → JSON Schema + 无 shell 校验 → ready 判定 → 指纹（输入/输出哈希）
```

顺序不能换：策略钉硬必须在最前（AI 与用户都改不动硬约束），指纹必须在最后
（"缺关键字段就清空工作流"会改变输出，哈希要反映最终产物）。

## 2. 四条不可回退的约束

1. **AI 不是决策来源**。方案由确定性规则引擎算出；AI 只能以 `recommendation`
   等级补充说明，且它的每条批注都要过与规则引擎**同一把尺子**（禁命令片段）。
   没配置提供方时 `ai_review = null`，界面显示"AI 未启用"——**绝不用模板文案假装分析过**。
   **【已被后续阶段补充】** P5.5 起可以配置 Provider 并**独立**运行复核
   （`deployment_proposal_ai_review`）；`generate` 本身仍然不调用模型，
   没配置 Provider 时依旧如实显示"AI 未配置"。见 `docs/p5.5-ai-knowledge.md`。
2. **每条关键结论自报家门**：`Statement.class` ∈ {fact, inference, recommendation, unknown}
   + `evidence[]`（来源：server_fact / artifact_fact / user_input / platform /
   knowledge / ai / derived）。没有证据的不许写成事实。
3. **冲突不静默**：知识库条目在同一 topic 上给出相反结论时产出
   `KnowledgeConflict`；能用**服务器实时事实**或**安全策略**裁定的就裁定并记下依据，
   裁定不了的进 `open_questions`（`BlocksPlan`）→ **不生成可执行计划**。
4. **缺关键字段就不出计划**：`ProposalOutcome.ready == false` 时
   `workflow.nodes` **必然为空**（`tests.rs` 有单测钉住这条）。

## 3. 输入 / 输出

输入（`engine::ProposalInputs`，全部来自本机模型 + 能力探测）：

| 输入 | 来源 |
| --- | --- |
| DeploymentApplication / ServiceUnit / ServiceRelation / DomainBinding | P5.0 表 |
| ArtifactRecord + **ArtifactAnalysis** | P5.1 导入：制品元数据 + 识别结果，经 `facts::derive_service_facts` 还原出端口 / 健康检查目标 / 环境变量名 / 制品是否被安全扫描挡住 |
| ServerCapabilityProfile | 实时探测（有会话）或最近一次扫描缓存 —— **实时事实优先** |
| CapacityProfile（含响应目标） | 容量问卷（P5.0 表 + v11 新增 `response_target_ms`） |
| SecurityPolicy | 应用级策略表；默认最保守，硬约束不可关 |
| KnowledgeResult | 内置知识库（编译期常量、带版本） |

输出必须符合 `checks::PROPOSAL_JSON_SCHEMA`（draft 2020-12），至少包含：
`summary` / `assumptions` / `unknowns` / `recommended_topology` /
`alternative_topologies` / `services` / `dependencies` / `capacity_recommendation` /
`domains` / `workflow`（nodes + edges）/ `risks` / `approvals` / `rollback_strategy` /
`knowledge_references`（+ `knowledge_conflicts`）/ `validation` / `fingerprint`。

## 4. 知识库

- **编译期常量 + 版本号**（`KNOWLEDGE_VERSION = kb-2026.09.1`）。
  知识可变 = 同输入不同输出 = 谈不上可复现；升级知识库就是改代码改版本号，
  旧方案的 `output_hash` 自然对不上（这正是审计要的）。
- 每条知识必须写 `source`（人可核对的文档 / 手册），写不出来源的不许进库。
- 冲突是**声明式**的（`conflicts_with`），且**只有真的在同一个 topic 上打架才算冲突** ——
  声明粒度太粗（如"自带数据库"vs"容器编排"）不会被报成冲突，否则会制造一堆
  假问题，最后逼用户随便点一个，反而背离"不静默"的初衷。
- 服务器事实 / 策略优先于知识库，且**必须解释"为什么没听知识库的"**
  （`Statement.id = topo-fact-overrides-knowledge`）。

## 5. 容量评估

```text
峰值 QPS（直接填）        ← 事实
  否则 平均 QPS × 3       ← 推断 + 假设"峰值是均值 3 倍"
  否则 并发 ÷ 响应时间     ← 推断；响应时间填了就用真的（事实），否则 0.5 秒（假设）
  否则 DAU × 5% ÷ 响应时间 ← 推断 + 两条假设
  否则 不知道              ← 未知（生产环境直接挡下来）
```

- 每 QPS 多少 CPU、每服务多少内存来自知识库的 `SizingRule`（JVM / 容器 / 通用三档），
  可追溯来源。
- 每条 `Assumption` 必须写 `if_wrong`（假设不成立会怎样）。
- `fits_on_server: null` = **没采集到硬件**，界面显示"尚未采集"，绝不猜 true。

## 6. 规则引擎

- **拓扑评分**：知识库权重 ×2 + 覆盖全部服务 +40 + 复杂度惩罚 − 未探测能力 − 规避项 −60；
  `Some(false)` 一票否决（不可行）；`None`（未探测）只记账并转成 `BlocksApproval` 未知项 —— 
  既不假装有，也不因此完全不可用。
- **工作流**：只产出 P5.0 的动作字典；节点 id = node_key（**确定性，不用 uuid**，
  否则输出哈希不可复现）；回滚节点是**独立汇点**，只由变更类节点的 `on_failure`
  边进入 —— "成功了还顺带回滚"这种路径在图上根本不存在。生成即自检
  （`validate_plan_graph`），不自检通过就清空并写明原因。
- **风险**：单节点 + 高可用目标、生产无 TLS、装不下、缺健康检查、知识库冲突未裁定、
  自建库迁移不可逆、无回滚计划、容量靠默认档估算。
- **审批**：动作级（迁移 / 推镜像 / 回滚）+ 生产部署方案级，`required` 恒为 `true`。
- **回滚**：自动/人工、恢复什么、**数据侧能不能回滚必须表态**（说不清就写"不能"）。

## 7. 校验分层

| 层 | 内容 | 挡住什么 |
| --- | --- | --- |
| `validate_schema` | 必需字段 / 类型 / 枚举 / 数值范围 / schema 版本 | **计划** |
| `validate_no_shell` | 禁用键（document 级）+ `params_json` 走 P5.0 的 `validate_params_json` + 结构化字段里的 `$()` / 反引号 | **计划** |
| capability | 拓扑不可行、资源装不下 | 批准 |
| secret | 制品里带密钥 / 凭据 | 批准 |
| path | 服务目录越出环境根目录 | 批准 |
| permission | 端口不在策略允许范围 | 批准 |
| risk | 生产无 HTTPS、知识库冲突未裁定 | 批准 |

两条刻意的取舍：

- **`args` 不在禁用键里**：`ServiceRuntime::NativeProcess.args` 是 P5.0 逐项校验过的
  合法字段；真正该禁 `args` 的地方是计划节点的 `params_json`（那里由 P5.0 负责）。
- **散文里的反引号不拦**：判断依据是"这段文本会不会进命令"。风险说明里引个文档名
  不该把生产方案挡下来 —— 假阳性比漏报更伤信任（用户会学会无视警告）。

## 8. AI 边界

- 接入点：`trait ProposalAdvisor { fn model(); fn review(&AiPrompt) -> Result<AiSuggestion, String> }`。
- 提示词版本 `PROMPT_VERSION` 进指纹；提示词**全文不落库**，只存哈希（里面可能含用户数据）。
- 批注不合格 → 进 `AiReview.rejected`（含原因），**不许静默丢弃**；提供方报错同样留痕。
- 当前**没有配置任何提供方**：`commands::deployment_proposal::AI_ADVISOR_ENABLED = false`，
  `generate` 一律以 `advisor = None` 调用。接入只需在这一层换 `Some(&advisor)`，
  方案结构、校验与指纹都不用改。

## 9. 可复现与审计

`ProposalFingerprint` = `engine_version` + `schema_version` + `model` + `prompt_version`
+ `knowledge_version` + `input_hash` + `output_hash` + `generated_at`。

- `input_hash`：规范化输入（服务 / 制品 / 域名 / 依赖 / 事实排序后）的 SHA-256。
- `output_hash`：**去掉 id / 时间戳**后的方案正文 SHA-256 —— 所以两次生成可以逐字节比对，
  也可以从库里存的那条记录重新算出来对账（`engine::output_hash`）。
- 同样的输入两次生成 → 两个哈希都相等（`tests.rs` 有单测）。

## 10. 持久化与 IPC

migration **v11**：`deployment_proposals`（整份 JSON + 指纹列，`status` 以列为准）
+ `deployment_security_policies`。方案是**不可变审计快照**，状态变更只改列不重写 JSON。

| 命令 | 作用 |
| --- | --- |
| `deployment_proposal_generate` | 生成并落库，返回 `ready / approvable / open_questions / blockers / proposal` |
| `deployment_proposal_list` / `_get` | 历史与详情 |
| `deployment_proposal_confirm` | 落成一份 **draft** 计划（节点 id 此刻才生成，审批标记原样保留） |
| `deployment_proposal_reject` / `_delete` | 拒绝 / 删除 |
| `deployment_policy_get` / `_save` | 安全策略（返回的是**钉硬之后**的策略） |

## 11. 界面

部署中心新增「方案」Tab，一页走完：**需求填写 → 分析 → 推荐方案 → 备选方案 →
风险/未知项 → 确认方案**（+ 历史方案）。要点：

- 证据等级、置信度、依据逐条可见；`unknown` 用醒目色标出；
- 指纹（输入/输出哈希、引擎、知识库、提示词、模型）始终显示；
- **未就绪就没有可点的确认**，只显示必须回答的问题与阻塞项；
- 确认后明确写"只生成草案计划，批准与执行在后续阶段"。

## 13. 已知缺口（交给后续阶段）

1. **不执行**：`confirm` 只落一份 `draft` 计划；批准（`PlanStatus::Approved`）与执行属于
   Workflow Engine + 部署执行阶段。
2. **服务事实依赖"精确匹配链"**：`ServiceUnit.artifact_id` → 制品 `source_ref`
   → 来源引用相同的导入任务 → 该任务的识别结果里 `name` + `source_path` 对得上的候选
   （`source_path` 由 `deploy_path` 去掉环境 `deploy_root` 得到；名字对不上时只按路径匹配）。
   任何一环对不上就**给空事实**，方案会如实写"端口未定 / 健康检查待确认"——
   宁可少给，也不猜。多次导入同一来源时取最近一次（按 `created_at`）。
3. **服务器硬件未采集**：`observed = None` → 只能给"需要多少"，核对"够不够"留给部署前。
4. **成本估算**是通用云主机量级（知识库里的单价），只作参考。
5. **知识库是内置的**：不支持用户自定义条目（要改就得改代码 + 版本号）。
